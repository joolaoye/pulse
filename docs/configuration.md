# Configuration

Pulse separates configuration into three product concepts:

```text
PodcastShow
    where episodes are published

PodcastPipeline
    how episodes are generated

Schedule
    when a pipeline runs
```

This separation is intentional. Publishing identity belongs to the show, generation behavior belongs to the pipeline, and execution timing belongs to the schedule.

Installation-wide provider credentials and Cloudflare resource identifiers are configured separately during `pulse init`; they are not podcast content configuration.

## Configuration ownership

| Scope | Owns | Examples |
| --- | --- | --- |
| Installation | Provider credentials and shared Cloudflare infrastructure | X bearer token, Anthropic API key, Voyage API key, ElevenLabs API key, Cloudflare account/resources |
| `PodcastShow` | Podcast identity and public publishing metadata | title, artwork, public base URL, RSS object key |
| `PodcastPipeline` | Source, interests, format, voices, and generation behavior | X list, interest profile, podcast profile, speakers, target duration |
| `PodcastPipelineSchedule` | When one pipeline should execute | local time, timezone, derived next run |

A useful rule is:

> If changing a value should alter **what listeners subscribe to**, it probably belongs to the show. If it should alter **what the next episode contains or sounds like**, it probably belongs to the pipeline. If it only changes **when generation happens**, it belongs to the schedule.

## PodcastShow

A `PodcastShow` is the publication identity that podcast clients see.

Create one with:

```bash
pulse show create
```

The current show configuration contains:

| Field | Purpose |
| --- | --- |
| `show_id` | Stable internal identifier for the show |
| `title` | Public podcast title |
| `description` | Public show description included in RSS metadata |
| `author` | Public creator, organization, or brand |
| `website_url` | Public webpage associated with the show |
| `artwork_url` | Permanent public URL for podcast artwork |
| `category` | Primary podcast category |
| `language` | Podcast language tag, defaulting to `en-US` |
| `explicit` | Whether the show contains explicit content |
| `verification_email` | Optional email used by podcast directories for feed verification |
| `public_base_url` | Public origin used to construct feed and media URLs |
| `feed_object_key` | Object-storage key where the RSS feed is published |

A typical show might use:

```text
show_id: pulse-daily
public_base_url: https://podcasts.example.net
feed_object_key: shows/pulse-daily/rss.xml
```

The resulting feed URL is:

```text
https://podcasts.example.net/shows/pulse-daily/rss.xml
```

You can inspect a persisted show with:

```bash
pulse show get <show-id>
```

### Public base URL

`PodcastShow.public_base_url` is the canonical public origin for that show.

It is deliberately **show-specific**, not a global environment variable. This allows different shows to publish through different public domains or paths while sharing the same Pulse installation.

Pulse combines the base URL with object keys to construct public URLs:

```text
public_base_url
    +
feed/audio object key
    ↓
public podcast URL
```

For example:

```text
public_base_url:
https://pub-example.r2.dev

feed_object_key:
shows/pulse-daily/rss.xml

feed URL:
https://pub-example.r2.dev/shows/pulse-daily/rss.xml
```

The base URL must not contain query parameters or a URL fragment.

The URLs referenced by the RSS feed must be publicly reachable. In particular:

- the RSS document;
- show artwork; and
- episode audio enclosures

must be accessible without Cloudflare API credentials or other private authentication if an external podcast client is expected to ingest them.

For production publishing details, see [Publishing](architecture/publishing.md).

## PodcastPipeline

A `PodcastPipeline` describes how Pulse turns source material into an episode.

A pipeline currently contains:

| Field | Purpose |
| --- | --- |
| `pipeline_id` | Stable identifier for the generation pipeline |
| `show_id` | Show that receives episodes generated by this pipeline |
| `podcast_profile` | Show-level editorial and conversational generation guidance |
| `speakers` | Speaker identities, roles, personas, and speaking styles |
| `speaker_voice_bindings` | Mapping from Pulse speakers to ElevenLabs voices |
| `interest_profile_markdown` | Interests used to evaluate retrieved material |
| `x_list_id` | Curated X list used as the source |
| `target_episode_duration_seconds` | Target duration supplied to episode planning |
| `enabled` | Whether the pipeline is eligible to run |

Create a pipeline with an interest Markdown file and podcast configuration JSON:

```bash
pulse pipeline create \
  ./config/interests.md \
  ./config/podcast.json \
  --pipeline-id pulse-daily \
  --show-id pulse-daily \
  --x-list-id <x-list-id> \
  --duration 1200
```

The show must already exist because the pipeline references it.

Inspect a pipeline with:

```bash
pulse pipeline get <pipeline-id>
```

## X list configuration

Pulse V1 retrieves from a curated X list.

The pipeline stores the list's stable X identifier as `x_list_id`.

Conceptually:

```text
X list
    ↓
timeline retrieval
    ↓
conversation/reply reconstruction
    ↓
Pulse ingestion and semantic processing
```

The X list is therefore more than a retrieval parameter: it defines the source universe for that pipeline.

Different pipelines can point at different X lists even when they publish to the same show.

For example:

```text
pipeline: ai-engineering
x_list_id: <AI / software list>

pipeline: startup-markets
x_list_id: <founders / investors list>
```

This is one of the main ways to create distinct Pulse "flavors."

For retrieval behavior, see [Retrieval](architecture/retrieval.md).

## Interest profile

The interest profile is Markdown stored with the pipeline.

It tells Pulse what material is worth carrying forward after retrieval and semantic deduplication.

A minimal profile can be:

```markdown
# Interests

I am interested in:

- software engineering
- AI infrastructure
- developer tools
- startups
- cloud platforms

Prefer technically substantive stories over hype.
```

The profile does not need a rigid schema. It is intentionally natural-language configuration so it can express preferences that are difficult to capture as a flat list of keywords.

Useful interest profiles tend to describe:

- subjects you care about;
- subtopics that deserve extra attention;
- types of stories you prefer;
- topics you want treated with more or less priority; and
- editorial preferences such as technical depth or practical relevance.

The interest profile affects relevance selection. The podcast profile, described below, primarily controls how selected material is framed and discussed.

In other words:

```text
Interest profile
    what should make the episode

Podcast profile
    how the episode should approach it
```

For scoring and semantic processing, see [Semantic processing](architecture/semantics.md).

## Podcast configuration JSON

The podcast configuration file contains:

```text
podcast_profile
speakers
speaker_voice_bindings
```

A valid single-host example:

```json
{
  "podcast_profile": {
    "name": "Pulse Daily",
    "purpose": "Help listeners quickly understand the most relevant technology and startup developments of the day.",
    "target_audience": "Software engineers, technical founders, and technology professionals who are comfortable with technical concepts but want concise context and analysis.",
    "editorial_style": "Prioritize technically substantive developments, explain why they matter, connect related stories, and avoid hype-driven framing.",
    "conversational_style": "Natural, analytical, and conversational, with speakers challenging assumptions and explaining ideas clearly without sounding scripted."
  },
  "speakers": [
    {
      "speaker_id": "host",
      "display_name": "Host",
      "podcast_role": "Primary host",
      "persona": "Curious, analytical, and skeptical of hype.",
      "expertise": [
        "software engineering",
        "technology",
        "startups"
      ],
      "speaking_style": "Conversational, concise, and direct."
    }
  ],
  "speaker_voice_bindings": [
    {
      "speaker_id": "host",
      "voice_id": "5u41aNhyCU6hXOcjPPv0"
    }
  ]
}
```

The same structure supports multi-speaker shows by adding more speaker profiles and corresponding voice bindings.

## Podcast profile

`PodcastProfile` is generation-wide editorial guidance.

It is distinct from `PodcastShow`.

`PodcastShow` describes the public podcast identity used for publishing. `PodcastProfile` describes the editorial identity used during episode generation.

The profile fields are:

| Field | Meaning |
| --- | --- |
| `name` | Name presented to generation agents as the podcast identity |
| `purpose` | Value the podcast should provide to listeners |
| `target_audience` | Intended listener and assumed level of knowledge |
| `editorial_style` | How topics should be selected, framed, and interpreted |
| `conversational_style` | How the generated discussion should feel and how speakers should interact |

For example:

```json
{
  "name": "Pulse Daily",
  "purpose": "Help listeners quickly understand the most relevant technology and startup developments of the day.",
  "target_audience": "Software engineers, technical founders, and technology professionals.",
  "editorial_style": "Prioritize technically substantive developments and avoid hype-driven framing.",
  "conversational_style": "Natural, analytical, concise, and conversational."
}
```

Avoid turning the profile into a large bag of overlapping fields. Its purpose is to provide stable, high-level editorial guidance across generation.

## Speakers

Each `SpeakerProfile` defines a persistent speaker identity.

The current fields are:

| Field | Meaning |
| --- | --- |
| `speaker_id` | Stable machine-readable identifier |
| `display_name` | Human-readable speaker name |
| `podcast_role` | Persistent role such as host, co-host, interviewer, or analyst |
| `persona` | Recurring perspective, temperament, and personality |
| `expertise` | Areas the speaker is naturally positioned to discuss |
| `speaking_style` | How that speaker should sound in generated dialogue |

Example:

```json
{
  "speaker_id": "analyst",
  "display_name": "Morgan",
  "podcast_role": "Analytical co-host",
  "persona": "Measured, skeptical, and detail-oriented.",
  "expertise": [
    "artificial intelligence",
    "software engineering",
    "technology markets"
  ],
  "speaking_style": "Precise and evidence-oriented, with careful qualifications and direct counterpoints."
}
```

Speaker IDs are used throughout planning, scripting, and audio production. Keep them stable once a pipeline is in use.

## Voice bindings

A `SpeakerVoiceBinding` maps a Pulse speaker to a provider voice:

```json
{
  "speaker_id": "analyst",
  "voice_id": "<elevenlabs-voice-id>"
}
```

The `speaker_id` must reference a speaker defined in the pipeline.

For a two-speaker configuration:

```json
"speaker_voice_bindings": [
  {
    "speaker_id": "host",
    "voice_id": "<host-voice-id>"
  },
  {
    "speaker_id": "analyst",
    "voice_id": "<analyst-voice-id>"
  }
]
```

Pulse preserves speaker identity through planning and scripting, then resolves the configured voice binding during audio production.

Voice selection therefore changes the rendered audio without changing the semantic identity of the speaker.

## Target episode duration

`target_episode_duration_seconds` belongs to the pipeline.

It controls the duration budget supplied to episode planning.

For example:

```text
900 seconds  = 15 minutes
1200 seconds = 20 minutes
1800 seconds = 30 minutes
```

Pulse currently requires a target of at least five minutes.

Duration is a planning target, not a post-generation audio trim. The generation pipeline allocates the episode structure against this budget before synthesis.

This matters because simply cutting generated audio to a target duration would destroy editorial structure and conversation continuity.

For generation details, see [Generation](architecture/generation.md).

## Enabled state

Every pipeline has an `enabled` flag.

New pipelines are enabled by default.

The flag is the source of truth for whether a scheduled pipeline is eligible to launch:

```text
schedule due + pipeline enabled
    → may run

schedule due + pipeline disabled
    → does not run
```

The schedule does not maintain a second independent enabled/disabled state.

This keeps execution state simple: disable the pipeline when you want scheduled generation to stop without deleting its configuration or schedule.

## Schedule

A schedule describes **when** a specific pipeline should execute.

Create or replace one with:

```bash
pulse schedule set <pipeline-id> \
  --time 06:30 \
  --timezone America/Chicago
```

Inspect it with:

```bash
pulse schedule get <pipeline-id>
```

Remove it with:

```bash
pulse schedule remove <pipeline-id>
```

The user-facing schedule is based on:

- the target `pipeline_id`;
- a local clock time; and
- an explicit timezone.

Pulse derives the next UTC occurrence from that configuration and persists scheduling state in D1.

The timezone must be explicit. Pulse does not silently interpret schedules using the developer machine's timezone.

For example:

```text
time:     06:30
timezone: America/Chicago
```

means "run this pipeline at 6:30 AM in Chicago local time," including the timezone's daylight-saving behavior.

Internally, due-time comparison uses a normalized UTC `next_run_at`.

Changing a schedule only changes persisted Pulse configuration; it does not modify Wrangler or redeploy the Worker.

For the scheduler architecture and duplicate-dispatch protections, see [Scheduling](architecture/scheduling.md).

## Pipeline flavors

A Pulse installation can support multiple pipelines with different source lists, interests, formats, and schedules.

For example:

### AI engineering briefing

```text
X list:
AI researchers, infra engineers, developer-tool builders

Interests:
model infrastructure
agents
developer tooling
systems engineering

Podcast style:
technical, analytical, skeptical of hype

Schedule:
weekday mornings
```

### Startup and technology markets briefing

```text
X list:
founders, investors, operators

Interests:
fundraising
product launches
startup strategy
technology markets

Podcast style:
business-oriented, concise, focused on implications

Schedule:
three times per week
```

### Research and learning digest

```text
X list:
researchers, educators, technical writers

Interests:
computer science
mathematics
AI research
learning resources

Podcast style:
explanatory, slower-paced, concept-first

Schedule:
weekly
```

These can either publish to separate shows or share a show, depending on the product you want listeners to subscribe to.

A practical rule:

```text
Different listener subscription / brand
    → separate PodcastShow

Same listener subscription, different generation recipe
    → separate PodcastPipeline attached to the same show
```

## What is global?

Most content configuration in Pulse is intentionally **not global**.

### Installation-wide

Configured during setup and deployment:

```text
X credentials
Anthropic credentials
Voyage credentials
ElevenLabs credentials
Cloudflare credentials/resources
shared runtime infrastructure
```

These tell Pulse **how to reach providers and infrastructure**.

### Show-specific

Stored on `PodcastShow`:

```text
public podcast identity
RSS destination
public base URL
artwork
show metadata
```

These tell Pulse **where and under what identity to publish**.

### Pipeline-specific

Stored on `PodcastPipeline`:

```text
X list
interest profile
podcast profile
speakers
voice bindings
target duration
enabled state
```

These tell Pulse **what to generate and how**.

### Schedule-specific

Stored independently for the pipeline:

```text
local run time
timezone
next occurrence
```

These tell Pulse **when to generate**.

Keeping those boundaries explicit is what allows one Pulse installation to host multiple independently configured podcast pipelines without turning environment variables into application state.
